MEDIUM - A refused seek stops Play/Pause and the More menu from working: app/lib/pages/conversations/wal_item_detail/wal_item_detail_native.dart:129-136 and app/lib/pages/conversations/recording_detail/recording_detail_sheet.dart:299-307 project the slider under one fixed id ('wal_position' / 'rec_position') with `enabled: transport`. Dart refuses any command for a disabled row (app/lib/mobile/native_ui/ios_native_surface.dart:423). Swift treats a slider as an edit and queues the latest drag value while a seek is pending (app/ios/Runner/NativeUI/NativeSurfaceView.swift:124-133). A refused edit whose id is still in the snapshot goes into `failedEdits` (:158-163) and stays there while that id exists (:52-53). From then on, every non-cancellation action is refused with `actionFailed` (:142-147). Realistic trigger: the user drags to the end, or past the real audio length (maximum is max(totalDuration, wal.seconds)), and playback finishes. AudioPlayerUtils._onPlaybackFinished clears `_currentPlayingId`, so the row turns disabled, the queued value is refused, and Play/Pause, back/forward and the menu all fail with the generic connection error until the person leaves the screen. The classic page has no such state. Fix: keep the disabled appearance but make the id depend on state (for example 'wal_position' while transport is enabled and 'wal_position_idle' otherwise, same for 'rec_position'). Swift then drops queued values and failed edits for the id that disappeared. Add a test: a refused seek, then a snapshot without that id, and 'wal_play' still dispatches.

MEDIUM - WalItemDetailPage changes its widget tree on the compile flag alone, even when native is unsupported: app/lib/pages/conversations/wal_item_detail/wal_item_detail_page.dart:131 returns `_nativeDetail(classic)` whenever `nativePresentationEnabled`, and :49-52 starts the asset copy on that flag alone. On a flag-on iOS that cannot render native (iOS < 16, or no renderer), the classic Scaffold is therefore nested inside an extra Scaffold + Consumer (wal_item_detail_native.dart:8-20). The page shows IosNativeSurface's loading spinner until the support check answers. The "WAL left device storage" handling also runs through the native interceptor (`_popOnceTransferred`, :14-20 and :61-66: a route-current guard, a single attempt, and it suppresses the success pop at wal_item_detail_page.dart:482) instead of the classic code at :164-172. This breaks the rule that flag-on but unsupported behaviour stays the classic page. Fix: use the home_content.dart idiom. Add `late final Future<bool> _nativeSupport = supportsNativePresentation();`, keep `if (!nativePresentationEnabled) return classic;`, and return `_nativeDetail(classic)` only when the FutureBuilder answers true (otherwise `classic`). Start the nativeAssetImageUri copy only after support is confirmed.
